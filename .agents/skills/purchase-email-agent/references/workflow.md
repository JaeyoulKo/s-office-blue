# 구매 이메일 검토 흐름

## 스토리보드에서 재구성한 흐름

1. 사용자가 제공한 이메일 관련 자료와, 사용 가능한 읽기 전용 MCP Tool의 조회 결과를 먼저 목록화한다. 도구가 없거나 권한이 없으면 사용자 제공 자료만 사용한다.
2. 전체 문맥으로 분류한다. 작업/승인 표현, Ariba, 구매·계약·견적·공급사 용어, 금액·수량·납기 신호는 보조 근거일 뿐 확정 근거가 아니다.
3. 비구매 메일은 공지/일반 업무 이메일로 간결히 브리핑한다. 구매·승인·계약 건은 구조화 검토로 진행한다.
4. 구매 및 승인 건은 해당 요청의 필수 정보가 충분한지 점검한다. 부족하면 실제 발송 대신 사용자 검토용 보완 요청 초안을 작성한다.
5. 기대효과 제시 여부를 확인한다. 정량적 주장은 근거와 단위를 보존한다. 스토리보드의 매출 증가, 비용 감소, 고객 유입, 업무 효율, 투자 회수는 예시이며 모든 건의 필수조건은 아니다.
6. 과거 계약 비교 필요성을 판단한다. 동일/유사 공급사·품목과 최근 사례가 있으면 유용하다. 해당 읽기 MCP capability가 있을 때만 MCP Tool 결과를, 없으면 사용자가 제공한 자료만 분석한다.
7. 논의 이메일은 첨부파일 유무·내용을 먼저 확인하고 본문/스레드를 분석한다. 스레드를 요약한 뒤 과거 자료 존재 여부를 확인한다. 회신/스레드 문맥, 공급사·품목, 사용자 제공 식별자로 매칭할 수 있지만 불확실한 매칭은 추론으로 남긴다.
8. 구매 승인 이메일의 이슈와 우선순위가 분명한 브리핑을 만든다. 자료 한계와 불확실성도 함께 남긴다.

## 스토리보드 기반 가정

- 스토리보드에는 UI 화면, 키워드 목록, 메일 목록, 링크, Ariba 결정, Excel/DB 저장이 보인다. 이 Skill은 문서 기반 하네스이며 이를 구현하거나 운영하지 않는다. 제품 구현 시 UI는 React/Next.js, 외부 시스템 접근은 MCP Tool로 분리한다.
- CFO/Finance Boss 등의 특별 수신자가 예시로 보이지만, 권한 정책·금액 기준·승인 역할은 명세되어 있지 않다. 수신자와 승인자 판단은 사용자 확인 사항으로 둔다.
- 저장/신규 레코드와 과거 데이터 조회가 보이지만, 현재 작업에 자료가 제공되지 않으면 조회가 수행되었다고 가정하지 않는다.
- 회신 기한, 금액 임계값, ‘최근 계약’의 정확한 기간은 명시되지 않았다. 임의로 만들지 않는다.
