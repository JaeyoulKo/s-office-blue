# 역할과 협업 방식

## 목적

모든 화면은 하나의 office-blue 시스템에 속한다. 전체 구조는 함께 사용하고, 각
Finance 담당자는 자신이 잘 아는 업무의 세부 내용을 채운다. 세부 내용을 다른 담당자가
작성해도 해당 화면이 별도 시스템이 되는 것은 아니다.

## 현재 설계 책임

| 영역 | 함께 정하는 큰 틀 | 세부 내용을 정하는 사람 |
| --- | --- | --- |
| 앱 구조와 공통 화면 틀 | 전체 구조 담당자 | 전체 구조 담당자와 Codex |
| 디자인 시스템 | 전체 구조 담당자 | 공통 변경은 함께 검토 |
| Start Point | 전체 구조 담당자 | 전체 구조 담당자와 Codex |
| 메일 브리핑 공통 화면 | 전체 구조 담당자 | 전체 구조 담당자와 Codex |
| 구매 승인 요청 플로우 | 전체 화면 안에서의 위치, 공통 디자인, 앞뒤 연결 | 해당 Finance 담당자와 Codex |
| 논의 이메일 플로우 | 전체 화면 안에서의 위치, 공통 디자인, 앞뒤 연결 | 해당 Finance 담당자와 Codex |

큰 틀에는 다음이 포함된다.

- 전체 정보 구조와 라우트 체계
- 공통 앱 셸과 내비게이션
- 기능 간 데이터 및 상태 계약
- 디자인 토큰과 공통 UI 사용 규칙
- Gmail 등 외부 연동 경계
- 접근성, 오류 처리, 테스트의 최소 기준

각 Finance 담당자가 Codex와 정하는 세부 내용에는 다음이 포함된다.

- 플로우 내부의 필드와 검토 항목
- 도메인별 판단 규칙의 화면 표현
- 기능 전용 컴포넌트 구성
- 세부 상태 전이와 예외 사례
- 기능 테스트와 화면 명세 보완

## 협업 규칙

1. 기능 팀은 `features/<feature-name>` 내부를 우선 수정한다.
2. 공통 UI 변경이 필요하면 사용 사례와 영향을 문서화해 별도 변경으로 제안한다.
3. 기능 전용 요구를 공통 컴포넌트의 기본 동작으로 넣지 않는다.
4. 다른 기능의 내부 경로를 직접 import하지 않고 공개 `index.ts`를 사용한다.
5. 새 라우트는 `screen-route-map.md`에 먼저 등록한다.
6. 새 시각 규칙은 디자인 토큰으로 승격할지 검토한 후 적용한다.
7. 업무 규칙이 바뀌면 해당 Skill 또는 업무 문서와 UI 명세를 함께 갱신한다.

## 통합 지점

각 플로우는 공통 검토 화면에 다음 정보를 같은 방식으로 전달한다.

- 어떤 종류의 메일인지
- 현재 검토 상태가 무엇인지
- 사용자에게 보여줄 핵심 요약
- 사용자가 다음에 할 수 있는 일

구체적인 데이터 이름과 개발 코드는 구매 승인 요청 및 논의 이메일 담당자의 화면 설명이
정해진 뒤 Codex가 만든다.
