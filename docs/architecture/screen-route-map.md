# 화면 및 라우트 구성

## 화면을 구분하는 기준

스토리보드의 모든 노드는 화면이 아니다. 다음 조건을 만족할 때만 독립 페이지로 만든다.

- 사용자가 URL로 직접 다시 진입할 필요가 있다.
- 새로고침 후에도 동일한 업무 대상을 복원해야 한다.
- 브라우저 뒤로 가기가 업무 흐름상 의미가 있다.
- 다른 팀이나 기능에서 해당 화면으로 링크해야 한다.

다음 항목은 페이지가 아니라 현재 페이지 내부 상태나 컴포넌트로 처리한다.

- 로딩, 성공, 오류, 빈 결과
- 확인 질문과 Yes/No 결정
- 누락 정보 경고
- 검토 체크리스트
- 이메일 상세와 초안 미리보기
- 완료 알림과 일시적인 진행 상태

## 1차 라우트 지도

| 경로 | 화면 | 책임 | 현재 구현 담당 |
| --- | --- | --- | --- |
| `/` | Start Point | 조회 조건 설정과 메일 브리핑 시작 | 현재 작업 범위 |
| `/briefing` | 메일 브리핑 | 검색 결과, 유형, 상태, 선택 | 현재 작업 범위 |
| `/reviews/[reviewId]` | 검토 작업 공간 | 선택한 메일의 검토 컨테이너 | 공통 셸만 현재 범위 |
| `/reviews/[reviewId]/purchase-approval` | 구매 승인 요청 | 승인 요청 검토와 후속 처리 | 공통 틀 포함, 상세 내용은 담당자 작성 |
| `/reviews/[reviewId]/discussion` | 논의 이메일 | 논의 내용 검토와 후속 처리 | 공통 틀 포함, 상세 내용은 담당자 작성 |
| `/settings/integrations` | 연동 상태 | Gmail 등 연결과 읽기 가능 상태 | 현재 작업 범위 |

구매 승인 요청과 논의 이메일 플로우도 하나의 office-blue 시스템과 공통 검토 여정에
속한다. 따라서 앱 셸, 라우트 위치, 상태 계약, 디자인 시스템, 기능 간 연결 방식은 전체
아키텍처에서 함께 정의한다. 담당 팀원은 이 공통 계약 안에서 각 플로우의 세부 정보
구조, 검토 항목, 업무 판단 UI와 테스트를 구체화한다.

## 공통 앱 셸

모든 업무 페이지는 같은 셸을 사용한다.

- 상단: 제품명, 현재 환경, 계정 메뉴
- 좌측 내비게이션: 시작, 메일 브리핑, 진행 중인 검토, 설정
- 본문: 페이지 제목, 설명, 주 작업 영역
- 보조 영역: 연결 오류나 권한 문제 같은 전역 알림

Start Point처럼 집중이 필요한 초기 화면은 좌측 내비게이션을 축소할 수 있지만 별도
디자인 체계를 만들지는 않는다.

## 화면 명세 템플릿

새 페이지를 만들기 전에 `docs/screens/<screen-name>.md`를 다음 형식으로 작성한다.

```md
# 화면 이름

## 목적
사용자가 이 화면에서 완료해야 하는 한 가지 목표

## 진입 조건
- 이전 상태 또는 URL

## 정보 구조
- 섹션과 표시 정보

## 주요 동작
- 사용자가 실행할 수 있는 동작

## 상태
- 초기
- 로딩
- 빈 결과
- 오류
- 성공

## 권한 및 안전 경계
- 읽기/쓰기 여부
- 추가 확인이 필요한 동작

## 완료 조건
- 다음 화면 또는 상태
```

## Start Point 범위

스토리보드 왼쪽 상단의 Start Point는 다음만 책임진다.

- Gmail 연결 상태 확인
- 조회 시작일과 종료일 선택
- 읽지 않은 메일 조건
- 최대 조회 건수 설정, 기본 50건
- 메일 브리핑 시작

메일 분류 결과나 구매 판단은 Start Point에 표시하지 않는다. 시작 동작 이후
`/briefing`에서 결과와 진행 상태를 보여준다.
