# 화면 개발 안내

## 이 문서의 목적

office-blue는 Finance 담당자와 개발 도구인 Codex가 함께 만드는 하나의 웹 시스템이다.
Finance 담당자는 업무 내용과 화면에 필요한 정보를 설명하고, Codex는 그 내용을 실제로
작동하는 화면 코드로 만든다.

개발 용어를 알 필요는 없다. 아래 세 가지를 분명하게 설명하면 된다.

1. 사용자가 이 화면에서 무엇을 확인해야 하는가?
2. 사용자가 어떤 버튼이나 선택 항목을 사용할 수 있어야 하는가?
3. 작업이 끝나면 다음에 어디로 이동하거나 어떤 결과를 보여줘야 하는가?

## 전체 화면 흐름

```text
시작 화면
  ↓
메일 브리핑
  ↓
메일 종류에 맞는 검토 화면
  ├─ 구매 승인 요청
  └─ 논의 이메일
  ↓
검토 결과와 다음 작업
```

구매 승인 요청과 논의 이메일은 별도 제품이 아니다. 같은 시스템 안에서 공통 화면과
디자인을 사용한다. 각 담당자는 자신이 잘 아는 Finance 업무 내용과 세부 검토 기준을
채우고, 전체 화면 구조와 공통 사용 방식은 함께 유지한다.

## 사람이 작성할 화면 설명

새 화면이 필요할 때는 다음처럼 평범한 문장으로 작성한다.

```md
# 구매 승인 요청 화면

## 사용 목적
승인자가 구매 요청의 필수 정보와 위험 요소를 빠르게 확인한다.

## 화면에서 보여줄 정보
- 요청자
- 공급사
- 구매 금액
- 구매 사유
- 누락된 필수 정보

## 사용자가 할 수 있는 일
- 원본 이메일 확인
- 누락 정보 확인
- 보완 요청 내용 확인
- 다음 검토 단계로 이동

## 특별한 상황
- Gmail 연결이 끊긴 경우
- 메일이 없는 경우
- 필수 정보가 누락된 경우
```

Codex는 이 설명과 디자인 규칙을 함께 읽고 화면과 필요한 파일을 만든다.

## 파일은 언제 생기는가?

MD 문서를 작성한다고 화면 코드가 자동으로 계속 생기지는 않는다. 실제로 “이 화면을
구현해줘”라고 요청했을 때 Codex가 필요한 TS, TSX, CSS 파일을 한 번 만들고 Git에
저장한다. 다음 작업부터는 기존 파일을 지우고 다시 만드는 것이 아니라 수정해서
발전시킨다.

파일 수가 늘어나는 것은 일반적이지만 처음부터 모든 파일을 만들 필요는 없다.

- 시작 화면 구현: 화면 파일, 입력 폼, 기본 스타일 정도만 생성
- 두 번째 화면 구현: 필요한 기능 파일을 추가
- 같은 버튼이나 입력 항목이 반복될 때: 공통 컴포넌트로 분리
- 화면이 실제로 늘어날 때: 폴더도 필요한 만큼 확장

즉, 설계 문서에는 전체 자리를 보여주되 실제 코드 파일은 사용할 때만 만든다.

## 문서 읽는 순서

Finance 담당자는 보통 이 문서와 자신이 맡은 화면 설명만 읽으면 된다. Codex와 개발자는
구현할 때 다음 상세 문서를 추가로 확인한다.

- `screen-route-map.md`: 어떤 화면들이 연결되는지
- `feature-ownership.md`: 큰 틀과 세부 내용의 담당 방식
- `frontend-architecture.md`: 실제 코드 파일 배치 규칙
- `docs/design-system/README.md`: 화면의 공통 디자인과 사용 방식
