# office-blue 디자인 시스템

## 목표

디자인 시스템은 화면을 비슷하게 보이게 하는 색상 모음이 아니라, 여러 업무 화면이 같은
정보 위계, 상태 의미, 상호작용 규칙을 사용하도록 하는 제품 계약이다.

쉽게 말하면 모든 화면에서 버튼, 입력칸, 글자, 색상과 알림을 같은 방식으로 보이게 하는
공통 규칙이다. Finance 담당자는 새로운 디자인 용어를 만들 필요 없이 필요한 정보와
업무 상태를 설명하면 되고, Codex가 이 규칙에 맞는 화면 요소를 선택한다.

초기에는 이 웹앱의 `components`와 `styles` 폴더에서 관리한다. 별도 패키지는 두 번째
앱이나 독립 배포 요구가 실제로 생겼을 때만 만든다.

## 디자인 방향

office-blue는 토스처럼 쉽고 명확한 사용 경험을 지향한다. 특정 서비스의 화면이나
브랜드를 그대로 복제하지 않고 다음 장점을 Finance 업무에 맞게 적용한다.

- 어려운 내용을 짧고 쉬운 문장으로 설명한다.
- 한 화면에서 가장 중요한 다음 행동을 분명하게 보여준다.
- 충분한 여백과 명확한 제목으로 정보의 순서를 이해하기 쉽게 만든다.
- 관련 정보는 카드와 구역으로 묶고 불필요한 선과 장식은 줄인다.
- 오류가 발생하면 원인만 표시하지 않고 사용자가 다음에 할 일을 함께 안내한다.

구매 검토와 비교 업무에는 많은 정보가 필요하므로 모든 화면을 지나치게 단순하게
만들지는 않는다. 시작 화면과 안내 화면은 간결하게 구성하고, 검토 화면은 표,
체크리스트, 근거 영역을 사용해 필요한 정보 밀도를 유지한다.

디자인 방향을 한 문장으로 정리하면 다음과 같다.

> 토스의 쉬운 사용성과 명확한 정보 위계에 Finance 업무에 필요한 검토 정보와 근거를
> 더한다.

## 색상 의미

스토리보드 도형 색상을 제품 UI 색상으로 그대로 복사하지 않는다. 스토리보드 색상은
노드 종류를 구분하기 위한 것이고 제품에서는 상태 의미가 우선이다.

| 의미 | 사용 예 |
| --- | --- |
| Brand | 주요 버튼, 현재 단계, 선택 상태 |
| Success | 완료, 충족, 연결됨 |
| Warning | 검토 필요, 정보 부족, 주의 |
| Danger | 실패, 차단, 되돌리기 어려운 작업 |
| Info | 안내, 진행 중, 보조 정보 |
| Neutral | 일반 텍스트, 경계, 비활성 상태 |

색상만으로 상태를 전달하지 않고 항상 텍스트, 아이콘 또는 레이블을 함께 사용한다.

## 토큰 구조

개발할 때는 개별 색상값보다 의미가 있는 공통 이름을 사용한다.

```text
기본 색상             상태 의미              실제 사용 위치
blue-600          -> color-action-primary -> button-primary-background
green-600         -> color-status-success -> badge-success-text
gray-200          -> color-border-default -> card-border
```

화면마다 `blue-600`처럼 색상을 직접 고르지 않는다. 공통 이름을 사용해 전체 색상 변경과
접근성 조정을 한 곳에서 처리한다.

## 컴포넌트 상태 계약

모든 상호작용 컴포넌트는 필요한 경우 다음 상태를 제공한다.

- default
- hover
- focus-visible
- active
- disabled
- loading
- invalid

업무 화면은 별도로 초기, 로딩, 빈 결과, 부분 성공, 오류, 권한 없음 상태를 정의한다.

## 접근성 기본 규칙

- 키보드만으로 모든 주요 동작을 수행할 수 있어야 한다.
- 포커스 표시를 제거하지 않는다.
- 폼 필드는 보이는 레이블과 오류 설명을 가진다.
- 상태 변화는 색상에만 의존하지 않는다.
- Dialog와 Drawer는 포커스 이동과 복귀를 관리한다.
- 표는 열 제목과 빈 결과 설명을 제공한다.
- 모션 감소 환경을 지원한다.

## 공통 컴포넌트 승격 기준

다음 조건을 모두 만족할 때만 기능 컴포넌트를 공통 영역으로 옮긴다.

1. 두 개 이상의 독립 기능에서 실제로 사용된다.
2. 입력과 출력이 업무 도메인에 종속되지 않는다.
3. 시각적 형태뿐 아니라 동작과 접근성 규칙도 동일하다.
4. 변형을 props로 계속 추가하지 않고 작은 API로 설명할 수 있다.

## 변경 절차

1. 필요한 사용 사례를 화면 명세에 기록한다.
2. 기존 토큰이나 컴포넌트로 해결 가능한지 확인한다.
3. 새 규칙이 필요하면 디자인 시스템 문서와 구현을 함께 변경한다.
4. 주요 상태와 키보드 동작을 테스트한다.
5. 영향받는 화면을 확인하고 변경 내용을 PR에 기록한다.
